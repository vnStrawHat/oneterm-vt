# Commit rules

## Format (Conventional Commits 1.0)
`<type>(<scope>)!: <subject>` + blank line + body + footers.
- type: `feat` new behaviour or public item; `fix` bug; `perf` measured speed/memory change; `refactor` no behaviour change; `test`; `docs`; `build` Cargo/deps/profiles; `ci`; `chore` everything else; `release` version bump commit made by scripts/release.sh (subject `release vX.Y.Z`).
- scope: a crate module or area: `parser`, `cell`, `intern`, `width`, `grid`, `reflow`, `selection`, `terminal`, `events`, `snapshot`, `search`, `input`, `graphics`, `pty`, `bench`, `docs`, `ci`, `release`, `workspace`. Omit only when the change spans most of the tree.
- subject: imperative, lower-case, no period, ≤72 chars. Body explains why, names the spec folder (`Spec: docs/specs/0002-parser`). Breaking API change: `!` after scope and a `BREAKING CHANGE:` footer.
- Every commit ends with the attribution trailer the session provides (`Co-Authored-By: ...`).
- version bump by type: `!` / `BREAKING CHANGE:` -> major, `feat` -> minor, `fix` / `perf` -> patch.

## When to commit
- Only green commits: fmt, clippy (`--all-features`), tests and docs all pass at every commit. Never commit WIP.
- Unit of commit = one roadmap phase (spec + implementation + tests + user chapter) as one commit, or two at most when the spec was finished in an earlier session (`docs(spec): ...` first, `feat(<scope>): ...` second).
- Review fixes (advisor findings, fmt/clippy fixups, typos) are folded into the phase commit before it is made; they never become their own commits.
- Separate commits only for: a bug fix after the phase landed (`fix`), a measured perf change (`perf`), CI/build changes (`ci`/`build`), a release (`release`).
- The orchestrator commits on its own as soon as a phase (or a review-fix round) is green; it never asks first. Agents never commit.
- The release kind (`patch|minor|major`) is the highest bump among commits since the last tag.
- Rebase/squash locally before push is fine; never rewrite pushed history.

## Release notes
- Generated by git-cliff (`cliff.toml`) from the commits between tags when a tag is pushed; shown in the GitHub release. There is no hand-written changelog.
- Only `feat`, `fix`, `perf` and breaking changes appear, so their subjects must read well to users and name the public item. `docs`, `test`, `ci`, `chore`, `build`, `refactor` and `release` are hidden.
- One commit per phase keeps the notes short.

## Examples
```
feat(parser): VT state machine, params, OSC/DCS caps and tier-1 bench

Phase 1 of docs/roadmap.md. Hostile input never panics; OSC grows to 8 MiB
only for codes the sink allows.

Spec: docs/specs/0002-parser
```
```
fix(grid): keep RowId stable when scrollback is trimmed on resize
```
```
perf(parser): memchr3 ground scan, plain_ascii 74 -> 91 MiB/s
```
